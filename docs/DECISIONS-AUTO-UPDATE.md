# 决策文档｜插件自更新体系（2026-09-25 用户逐项拍板）

## 1. 为什么需要这份决策

本机 DSH 的插件安装形态在 2026-09-24 前后整体切到**桌面客户端 + `desktop` profile**，插件由 pnpm 按 `github:songoao25/dsh-bottom-info-bar` 拉成**独立快照**（commit 钉在 lockfile）。仓库里的任何 git 操作都不会影响这份快照。用户报「本地为什么没有更新到最新」，进一步追问：**「插件到底应该怎么更新？你要设计好体系。」**

## 2. 事实核查（先说清能力边界，再谈方案）

| 事实 | 证据 |
| --- | --- |
| 宿主插件管理**没有**「更新」这个动作 | `dsh-plugin-manager` 的安装结果为 `stage: remove \| install \| enable`；`typert.host.js` 接口只有 install / remove / enable / setPluginEnabled；官方 README 无任何更新流程 |
| 直接重装同一地址会被拦 | 插件页 locale 存在 `already-installed` / 「该插件已安装」，`inspect()` 的 `problem` 枚举包含 `already-installed` |
| 桌面端**没有** dsh 命令 | `/Applications/DeepSeek Harness.app/Contents/Resources/runtime/bin/` 下只有 `node`，无 `dsh`；`dsh` 也不在 PATH |
| 卸载重装**不丢数据** | 用户 2026-09-25 实测卸载重装后，`~/.dsh/dsh-bottom-info-bar/` 的 `usage-records.json`（3 条）、`usage-records.journal.jsonl`、`settings.json` 均完好 |
| 本插件**零运行时依赖** | `package.json` 的 `dependencies` 为空，`peerDependencies` 只有 react；分发内容仅 `lib/`、`cordis.patch.yml`、`locale/*.json` |
| 同生态没有先例 | 本机 `dsh-chatgpt-subscription`、`dsh-opencode-session` 均无更新机制；DSH 自带插件随 app 更新 |

**结论**：更新（把新代码替到本机 profile）在制度上只有宿主的插件管理器能做，而它偏偏没有这个动作。因此用户侧唯一路径是「卸载 → 重装」——这正是用户说的「太蠢了」。要在官方支持之前改善，只能由插件**自己更新自己**。

## 3. 决策记录（用户逐项拍板，原文照录）

### 决策 1 · 更新机制选哪条路

> 问：更新机制选哪条路？（宿主不支持已成定局，只能我们自己想办法）

- **用户选择：做一键自更新（推荐）**
  选项原文：「插件自己下载新版、替换自己的代码，你点一下 + 重启 DSH 就完成。优点：真正方便，且我们插件零运行时依赖，不碰依赖树，风险可控。缺点：绕过了宿主的包管理，你在插件页装别的插件时可能把它还原回旧版（再点一次即可）。」
- 未选：只做提示引导（保底）／两者都做。

### 决策 2 · 更新怎么触发

> 问：一键更新怎么触发？

- **用户选择：全自动（除重启）**
  选项原文：「下载 + 提示都自动，但 DSH 重启必须你做（插件无法重启宿主）。」
- 未选：我点按钮才更新（推荐）／自动下载，我只重启。

**落地要求**：插件启动后自行检测 → 有新版本即自动下载、校验、替换包文件 → 界面提示「重启 DSH 生效」。**用户无需点任何按钮**；同时仍要提供手动「立即检查 / 重试」入口，供自动流程失败时使用。

### 决策 3 · 版本提示放在哪里

> 问：版本提示放在哪里？（你说让我综合评估，这是我的推荐）

- **用户选择：设置页为主 + 信息栏短标记（推荐）**
  选项原文：「设置页常驻「版本与更新」区（当前版本 / 最新版本 / 一键更新）；信息栏只在真有新版时出现一个短标记，升完即消失，不常驻占位。」
- 未选：只在设置页／信息栏也常驻显示。

### 决策 4 · 更新方式与提示分区（2026-09-25 第二轮，用户主动推翻「全自动」）

用户的反思原话：

> 关于这个自动更新，我反思了一下，不能做到完全自动更新。就算要做完全自动更新，也要给用户提示。也就是说，要在设置页里给更新做一个开关，让用户选择「全自动更新」还是「手动更新」，同时在后台的设置页里也要提供一个「检查更新」的按钮。

- **拍板 4a**：更新方式改成**二选一**（「全自动更新」/「手动更新」），不是开与关的开关；另配「检查更新」按钮。
- **拍板 4b**：设置页**不新增**「简洁模式 / 完整模式」选择项（用户选择「不加」）。模式仍只由点击信息栏底行切换；设置页只在字段小字与分组说明里讲清「该字段属于哪个模式」。
  被问的原话：「「简洁模式 / 完整模式」要不要在后台设置页也加一个开关？（现在只能点信息栏底部那行切换，设置页里看不到、也改不了）」
- **拍板 4c**：「提醒信息」列表**收录全部提醒类字段（共 8 条）**，每条独立开关。

用户给出的三条调整原话（定义为验收口径）：

> 1. 模式显示逻辑：我们将模式分为「简洁模式」和「完整模式」。(a) 简洁模式：只显示插件信息。(b) 完整模式：插件信息和原生信息一起显示。
> 2. 开关控制逻辑：后台插件页的开关只需单纯地控制「开」和「关」，不需要去判断当前是简洁模式还是完整模式，开关与模式是不冲突的。
> 3. 新增「提醒信息」列表：在插件信息里的更新提醒、失败提醒等，可以单独拿出来。使用和原生信息、插件信息相同的组件，再做一个下拉列表，作为第三个列表，叫做「提醒信息」。这样用户就可以单独控制这个提醒信息的开关。

**落地口径（三条同时成立才算做完）**

| 调整项 | 具体做法 |
| --- | --- |
| 模式显示 | 保持既有 `infoDensity`：`compact` = 只显示插件信息，`full` = 插件信息 + 原生信息。原生组的 6 个字段在渲染层由 `full &&` 门控，**开关状态不受模式影响** |
| 开关解耦 | 字段开关只读写 `fields[id]`，任何代码路径都不得因模式变化去改写开关，也不得因开关状态去改写模式 |
| 提醒信息 | 新增第三组 `notice`（顺序为 原生信息 → 插件信息 → 提醒信息），收纳 8 条：更新提醒、更新失败提醒、余额更新失败、用量更新失败、更新失败提示、记录未保存提醒、缺少密钥提示、暂不支持提示 |

### 决策 5 · 设置页更新区的组织（2026-09-25 第三轮，用户主动提出「乱」）

用户原话：

> 这个版本更新的逻辑需要修改一下。目前版本更新里有一个固定的说明，下面可以切换「手动更新」和「全自动更新」，还有一个「检查更新」。你看一下怎么组织一下。现在感觉就是乱加上去的，没有成体系，很奇怪。
> 另外，全自动更新实现了吗？更新功能实现了吗？

**先回答「实现了吗」**（体检结论，不是看代码推断，是当场真跑）：

| 问 | 答 | 证据 |
| --- | --- | --- |
| 更新功能实现了吗 | 是 | 临时目录假装一台装着 1.19.1 的机器 → 真去 npm 拉 1.19.2 → 校验 → 替换成功（磁盘版本变 1.19.2、旧代码被换掉、备份与日志齐备、依赖树未动） |
| 装坏了会怎样 | 不会坏 | 喂一个半截坏包：直接放弃、磁盘一个字节未变、无残留临时文件、失败记入日志 |
| 全自动更新实现了吗 | 是，且当时正在运行 | 本机 `update-state.json` 的 `lastCheckAt` 正是 DSH 当次启动后 8 秒那次检查 |

**同时点出 4 处没到位**，其中三处正是「乱」的来源：

1. 同一套机制在卡片说明、更新方式说明、状态行里讲了三遍（文字墙）；
2. 「回滚到上一版」一旦更新成功就永久常驻 —— 判据用了永不清除的 `pendingVersion`；
3. 全自动模式下点「检查更新」会重复下载同一个版本（`&& !manual` 绕过了防重）；
4. 状态文件里记着「上次检查时间」，界面不显示，用户无法确认它有没有在干活。

**拍板（用户逐项选择）**

- **5a 整体结构：分三层「状态 — 设置 — 兜底」**。① 状态层只读事实：一句结论（大字）+ 运行中版本 / 最新版本 / 上次检查（小字）；② 设置层是这一块唯一的决策项：更新方式二选一；③ 兜底层平时不占位，只在需要处置时出现。
  未选：保持现有三段只做瘦身；设置页只留一行、其余挪到信息栏（信息栏标记当前打不开设置页，能力受限）。
- **5b 更新方式仍用二选一，说明随选中项变**。选中「全自动更新」只显示全自动那句，选中「手动更新」只显示手动那句，不再把两条说明并排摊开成一段。
  未选：改成一个「自动更新：开 / 关」开关 + 一个「立即更新」按钮（与决策 4a 的「二选一」不是同一套说法）。
- **5c「检查更新」与「回滚到上一版」按需出现**。「检查更新」只在「手动更新」方式下渲染（全自动时它做的是已经做完的事，点下去反而重新下载）；「回滚」只在真需要处置时出现（新版已装好待重启，或上次更新失败），并配一句说明为什么会出现。已更新并重启完成之后它不再占位。
  未选：检查常驻 + 回滚收进折叠区；两者都常驻但降级成小字。
- **5d 自动检查保持只在启动时查一次**，不新增周期复查。
  理由（用户认可的口径）：装好也必须重启才生效，而重启本身就会触发下一次检查；加周期只会多打请求，换不来更早生效。
  代价（明写在文档里）：DSH 长期不重启的期间，即使发布了新版本也不会被自动装上 —— 设置页的「上次检查」会显示它上次是什么时候查的，用户据此可判断。

**顺带修掉的两个 bug**（体检发现，属实现缺陷，无需拍板）

- 手动方式下点「检查更新」重复下载同一版本：`diskVersion() === latest.version` 的防重分支上原来挂着 `&& !manual`，去掉。手动只表示「自动关掉时授权下载」，不是「绕过防重」。
- 「回滚到上一版」永久常驻：`canRollback` 去掉 `!!state.pendingVersion`，改为 `restartDirection === 'update' || !!state.lastError`。

**失败原因讲人话**（同一轮加入）

`state.lastError` 原样存技术报错（如 `unexpected end of file`），界面只能把它甩给用户。现在引擎侧用 `describeUpdateError()` 把报错归一成稳定代号（incomplete-download / integrity-mismatch / download-failed / too-large / payload-mismatch / payload-unsafe / check-failed / unknown），界面按代号翻译成中英人话；原始报错写进 `update-log.jsonl`。归一函数同时认「代号」与「原始报错」，因此历史 state 文件里的老值也能被正确翻译。

## 4. 设计

### 4.1 更新流水线（宿主进程内，全自动）

```
启动后延迟（避开启动高峰）
  → GET https://registry.npmjs.org/dsh-bottom-info-bar/latest 取最新版本
  → 与「运行中版本」比较，非更高则结束
  → 下载 tarball（https://registry.npmjs.org/dsh-bottom-info-bar/-/dsh-bottom-info-bar-<ver>.tgz）
  → 校验：tarball 完整性（registry 的 integrity/shasum）+ 解包后 package.json 的 name/version 匹配
  → 备份当前包文件到 ~/.dsh/dsh-bottom-info-bar/backup/<version>/
  → 原子替换包内文件（lib/、locale/、cordis.patch.yml、package.json；绝不触碰 node_modules 依赖树）
  → 记录状态：已更新到 <ver>，待重启激活
  → 界面提示「重启 DSH 生效」
```

### 4.2 硬边界（不可越界）

1. **只写自己**：目标目录必须是本插件包自身目录（由 `import.meta.url` 推导），路径解析后必须落在该目录内，禁止 `..` 逃逸。
2. **不碰依赖树**：只替换插件包内文件，不执行 pnpm / 不写 profile 的 `package.json` 与 lockfile。
3. **只升不降**：仅当远端版本**严格高于**运行中版本时才动作；同版本或更低一律跳过（防投毒与误回退）。
4. **先备份后替换**：替换前完整备份，失败自动回滚；保留最近若干份备份。
5. **校验先行**：校验不过绝不落盘。
6. **可关闭 / 可选方式**：设置页给「更新方式」二选一 —— 「全自动更新」（默认）或「手动更新」；选手动后自动流程只检查不下载，必须由用户点「检查更新」才执行（决策 4a）。

### 4.3 已知风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 用户在插件页做任何包操作（装别的插件等）会按 lockfile 把本插件还原回旧版 | 自动更新是**每次启动都跑**的，被还原后下次启动会再次自动更新回来（自愈） |
| 替换到一半进程被杀，包目录残缺 | 先解包到临时目录并校验，再逐文件原子替换（写临时文件 + rename）；失败回滚备份 |
| 新版有 bug 导致插件启动失败 | 保留备份 + 设置页提供「回滚到上一版」；终极兜底仍是插件页卸载重装 |
| 宿主未来加完整性校验或更新按钮 | 本机制设计为可整体摘除；届时改为调用宿主能力 |
| 插件自动改写自己的安装文件属敏感操作 | 默认开但可关；所有动作写日志到 `~/.dsh/dsh-bottom-info-bar/update-log.jsonl` |

### 4.4 界面

- **设置页「版本与更新」区**（常驻，三层结构，见决策 5a）：
  - ① **状态**：一句结论（大字）+ 一行事实（运行中版本 · 最新版本 · 上次检查时间）。当前环境不支持自更新时，结论换成「当前环境不支持自动更新」，事实行里补上原因。
  - ② **设置**：唯一决策项「更新方式」两段式选择（`全自动更新` / `手动更新`），说明跟着选中项变；「检查更新」只在手动方式下出现。
  - ③ **兜底**：只在需要处置时出现 —— 新版已装好待重启、或上次更新失败时给出「回滚到上一版」，被暂缓时给出「允许更新到 X」，并先用一句小字说明为什么会出现。
  - 读不到更新状态时（宿主进程还没加载到这一版插件）整块保留并说明「重启 DSH 后就会出现」，绝不静默消失。
  - 失败原因用一句人话讲（引擎代号 → 字典文案），原始报错留在 `update-log.jsonl`。
- **信息栏**（只在需要用户动作时出现两枚短标记，平时不占位）：
  - 「重启生效」：新版已替换到磁盘、内存仍在跑旧代码（`pendingRestart`）。受 `fields.updateNotice` 开关控制。
  - 「更新失败」：上次自动更新失败。受 `fields.updateFailure` 开关控制。
  - 两枚标记**只作提示**：客户端插件只 `inject: ['slots', 'locale']`，没有「打开设置页」的能力，因此点击一律 `stopPropagation`（否则会冒泡到根节点把简洁/完整模式切走）。**不存在「点击跳设置页」**。
  - 标记挂在信息栏主行，简洁模式与完整模式都可见；它属于「提醒信息」组，与模式无关，只受自己的开关控制。

## 5. 验收标准

1. 版本比较严格：远端等于或低于本地时不下载、不替换。
2. 校验失败（完整性 / name / version 任一不符）时不落盘，状态记为失败且不破坏现有安装。
3. 替换为原子操作：注入「替换中途失败」后，包目录仍是替换前的完整内容（回滚生效）。
4. 路径安全：构造逃逸路径的输入被拒绝。
5. 不碰依赖树：更新前后 profile 的 `package.json` 与 `pnpm-lock.yaml` 字节不变。
6. 更新方式可选：选手动后自动流程不产生下载；点「检查更新」才执行（且不带 `force`，不解除回滚暂缓）。
7. 设置页结构（决策 4b / 4c）：字段卡恰三张，顺序为原生信息 / 插件信息 / 提醒信息；提醒组恰 8 条且每条独立开关；**设置页不出现简洁/完整模式开关**。
8. 开关与模式解耦：信息栏两枚更新短标记只受 `fieldVisible` 门控，任何模式下都不会因模式切换而消失/出现；原生组 6 个字段仍由 `full &&` 门控。
9. 中英文字案齐备：代码里引用的每个版本与更新键、注册表每个 label/note 键、三组标题键都必须在字典里（漏键会把键名显示给用户）。
10. `node tests/run-all.mjs` 全绿；`lib/` 重建并提交。

## 6. 与既有约束的关系

- 本机制**不修改** `package.json` 的 `version`、`.release-please-manifest.json`、`CHANGELOG.md` —— 版本号仍归 Release Please 独占（CI 守卫不变）。
- 本机制**不替代** `install.sh` / 一键安装；新装用户仍走原有路径。
- 本机制**不放宽**任何既有测试与发布链条契约。

## 7. 怎么验证「更新真的能用」（可复用的真机端到端验证）

单测跑的是桩依赖，证明不了「真实网络 + 真实 tarball + 真实替换」这条路通。要证明它，用一个临时目录假装一台装着旧版的机器，把引擎指过去跑一次 —— **全程不碰本机安装**：

```js
// 1. 造一台假机器：把本机已装的包复制到 /tmp/bib-verify/pkg，
//    再把 pkg/package.json 的 version 改成更旧的一个（例如 1.19.1），
//    并在 pkg/lib/client.js 末尾塞一行 '// OLD-BUILD-MARKER'
// 2. createSelfUpdater({ packageDir: '/tmp/bib-verify/pkg', dataDir: '/tmp/bib-verify/data', runningVersion: '1.19.1' })
// 3. await updater.run({ manual: true })
// 4. 断言：package.json 变成 npm 上的最新版、标记行消失、备份目录里是更新前的内容、
//    update-log.jsonl 里有 { event: 'updated' }、pkg 下没有 node_modules
```

失败路径同样要真跑一次：拿真实 tarball 截断成前 100 字节再喂给引擎，断言 `lastError` 变成 `incomplete-download`、`package.json` 字节未变、没有 `.update-tmp` 残留、日志里有 `update-failed`。

2026-09-25 第三轮就是这么回答用户的「更新功能实现了吗」的，两条路径都过。

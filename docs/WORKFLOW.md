# 日常开发流程（WORKFLOW）

> 面向：仓库主人 + 任何接手本项目的 AI Agent。
> 如果你只想知道「我该做什么」，看下面第一节就够了；Agent 请连同 `AGENTS.md` 一起读。

---

## 一、你（人）只需要做两件事

| 你要做的 | 怎么做 |
|---|---|
| **① 说需求** | 用大白话告诉 Agent 想干什么，例如「信息栏余额偶尔不刷新，查一下」「加一个显示今日 token 数的字段」。不用懂技术，不用说版本号。 |
| **② 看到「发布 PR」时说一声「发」** | Agent 会自动发现它，或你自己在仓库 Pull requests 里看到标题像 `chore(main): release 1.10.20` 的那个。回一句「发」，它就合并并自动发布到 npm。 |

**其余全部自动。** 你不需要：改版本号、写更新日志、打标签、手动发布、删分支。

> 为什么发版要你点一下？因为「对外发布」是不可撤销的动作（npm 上的版本不能覆盖）。
> 这道闸门是**故意的**：日常开发全自动，唯独发版需要一次明确确认。
> 万一你一段时间没确认，也不会有任何东西坏掉——只是新版本排队等着发。

---

## 二、完整流程长什么样

```
你说需求
   │
   ▼
Agent：从最新 main 开分支 → 改代码 → 补测试 → 跑全量测试 → 提 PR
   │
   ▼
CI 自动跑测试 + 安全扫描
   │
   ├─ 失败 → Agent 自己修，重新提
   │
   ▼
自动合并进 main（你自己的 PR 不需要人工点）
   │
   ▼
Release Please 自动：算版本号 → 写 CHANGELOG → 开「发布 PR」→ 停住
   │
   ▼
【你确认】回一句「发」          ← 全流程唯一需要你的地方
   │
   ▼
自动打标签 v1.10.20 → 自动发布到 npm
   │
   ▼
用户端：信息栏下次启动会显示红色「有新版本」提醒
```

## 三、三种常见情况的差别

| 情况 | 你要做的 | 说明 |
|---|---|---|
| **修 bug** | 说清楚现象 | Agent 会先复现、找到根因再改。**要求写出能失败的测试**，否则修了不知道有没有修对。 |
| **加 / 改功能** | 说清楚想要什么效果 | 涉及界面的一并说明期望观感；Agent 会补测试与文档。 |
| **只改文档 / 配置** | 说一声 | 这类改动（`docs:` / `test:` / `ci:` / `chore:`）**不会触发新版本**，因为 Release Please 会忽略它们——这是正常的，不是漏发。 |

## 四、Agent 必须遵守的硬规矩（CI 会自动拦）

这些已经写成自动化检查，**违反就合不进去**，不是靠自觉：

1. **不许手工改版本号**（`plugin/package.json` 的 version、`.release-please-manifest.json`、`CHANGELOG.md`）。版本号只归 Release Please 管。
2. **不许裸读宿主服务属性**（`ctx.某个服务名`）。这是本仓库踩过三次的坑，必须用 `inject` 声明 / `ctx.get()` / 带 `try` 兜底三种写法之一。
3. **项目记忆只能写在根目录 `MEMORY.md`**，不许自建工具专属的记忆目录。
4. **不许拆掉发布闸门或基准钉子**（`tests/test-release-chain.mjs` 会检查）。
5. 提交信息遵循 Conventional Commits（`fix:` / `feat:` / `docs:` / `test:` / `ci:` / `chore:`）——**它直接决定版本号怎么涨**：`fix:` 涨补丁位、`feat:` 涨次版本位。
6. **发布后必须收尾**（2026-09-13 用户明确要求）：每次发布完成后，Agent 要 ① 把复盘写进 `MEMORY.md`；② 写一份**能直接发到社区 / 微信群的更新通知**，用大白话说清「修了什么 bug、更新了什么功能」，追加到 `docs/ANNOUNCEMENTS.md`；③ 把通知**正文原文**发给用户——不加任何包装说明、推荐或追问，也不用 Markdown 标记，用户要的是选中就能直接粘贴的纯文本。

判断标准就一条：**提交前跑一次 `node tests/run-all.mjs`，全绿再提 PR。**

## 五、如果要动「发布」相关的文件

`release-please-config.json`、`.release-please-manifest.json`、`.github/workflows/release-please.yml`、`.github/workflows/publish-npm.yml`、`.github/workflows/auto-merge-own.yml` 这五个文件是**一条链条的不同环节**，改任何一个都可能让链条断掉，而且**可能静默失败**（GitHub 上有发布页，npm 上永远没有新版，且不报错）。

改完必须跑全量测试：`tests/test-release-chain.mjs` 会用 14 条断言确认链条完好。契约细节与「改错会导致什么后果」见 `AGENTS.md` 的「发布机制」章节。

## 六、一句话总结

> **你负责「说要什么」和「确认发版」，其余交给 Agent 和自动化。**
> **Agent 负责改对、测到、写清楚，并且不许碰版本号。**

# 决策文档｜信息栏设置页从 0 重构（2026-09-22 用户逐项拍板）

## 1. 为什么重构

连续四轮在「色点外环被裁」「按钮对不齐」上打补丁后，用户明确指出这是**舍本逐末**，要求从 0 重新审计。独立审计结论：

| 症状 | 表面 | 真正的根因 |
| --- | --- | --- |
| 列表极长、看着乱七八糟 | 32 个字段行、每行占 2 行 | 把「调色板」当成行内控件：7 个色点 + 系统取色器 + hex 输入 = 9 个控件硬塞进一行，被迫折行 |
| 一折叠就是全部折叠、一展开就是全部展开 | 折叠很蠢 | 折叠状态只有页面级一个 `fieldsCollapsed`，32 行共用一个折叠 |
| 有的行宽有的行窄 | 视觉上不齐 | 「主/世界时间」「自定义文字」这类**带参数的字段**把 5 个胶囊 + 时区选择框塞进了「显隐开关」这一行 |
| 改颜色的交互不像别的软件 | 交互生造 | 行业常规（macOS / Notion / Figma）是**行内一个色块 → 点开弹层**，没有一款把 7 个色点摊在列表行上 |

连带确认（虽然已随重构作废）：色点选中态的白环实测 **56×60**（理想整圆 60×60），横向少 2px 逻辑像素 —— 形状本身就不是正圆，不是「被裁」，是控件在 flex 行里被压扁。

## 2. 决策记录（用户逐项拍板，原文照录）

### 决策 1 · 改文字颜色的交互

> 问：改文字颜色的交互，采用哪一种？
- **用户选择：行内色块＋弹层（推荐）**
  选项原文：「行内只留一个色块（显示当前色，未设置时显示斜线）。点开宿主 Menu 弹层：6 个预设色 + 「自定义…」呼系统取色器 + 「恢复默认」+ hex 输入。每行 9 个控件降到 2 个，列表长度直接减半。这是 macOS/Notion 的常规做法。」
- 未选：只要系统取色器 / 色块＋hex 且预设进弹层。

**落地要求**：字段行右侧只剩「开关 + 一个色块」；色块点开 primitives `Menu`；菜单项依次为 6 个预设色（带色点）、「自定义…」（触发系统 `<input type="color">`）、「恢复默认」、hex 输入框。行内**不再**渲染 7 个色点、不再渲染独立的取色器色井。

### 决策 2 · 折叠结构

> 问：折叠结构怎么组织？
- **用户选择：两个分组独立折叠（推荐）**
  选项原文：「「原生字段」「插件字段」两组各自独立折叠，用宿主原生 DisclosureRow，组头带计数（如「已启用 12/18」），默认折叠，搜索命中自动展开。」
- 未选：按语义细分 5–6 组 / 保留总折叠只折行内参数区。

**落地要求**：删除页面级 `fieldsCollapsed` 单一状态；两个分组各自持有一个受控 `open` 状态；组头用 primitives `DisclosureRow`（`open` + `onToggle` + `expandable`），标题右侧带「已启用 N/M」计数；默认折叠；搜索有输入时两个分组自动展开。

### 决策 3 · 带参数的字段（主/世界时间、自定义文字）

> 问：「主/世界时间」和「自定义文字」这类带参数的字段怎么放？
- **用户选择：独立成设置区（推荐）**
  选项原文：「从字段行里拆出来，做成独立的「时间与日期」「自定义文字」设置区（用宿主 settings-form 字段），开关关掉时整区隐藏。字段行从此不再塞 5 个胶囊和时区选择框。」
- 未选：嵌在字段行、开关开时才展开。

**落地要求**：新增两个独立设置区（照宿主 `settings-form/fields.module.css` 字段基线：`.field { flex-direction:column; gap:6px; padding:12px 0 }`、`.field + .field { border-top:.5px solid border-l2 }`、`.label { 13/500 }`、`.input { height:34px; r8; padding:0 12px }`、`.hint { 12/1.5 }`）；对应字段开关关闭时整区隐藏。

### 决策 4 · 页脚「重置」的二次确认

> 问：页脚的「重置」要不要加二次确认？
- **用户选择：加二次确认（推荐）**
  选项原文：「用宿主原生 RiskConfirmation，重置前弹确认。现在是一点就把 32 个字段和所有颜色全清掉，破坏性操作没有确认。」
- 未选：保持一键重置。

**落地要求**：重置按钮点击后打开 primitives `RiskConfirmation`（勾选确认前「确认」按钮禁用），不再直接执行。

## 3. 实施要点

- 字段行照宿主 `settings-form` 基线：左「标签 + 说明」，右「开关 + 色块」，**单行**，不再折行。
- 所有度量继续走 `.bib-set-root` 的 `--bib-*` token 层，规则只准引用变量，不准写裸数字。
- 行几何继续照宿主 `.X_2TxG_row`：`padding: 12px 2px` + `0.5px` 下边线、末行无线（配置区下方紧邻的就是宿主自己的 `RowsSection`，两者要上下对齐）。
- 原生组件一律只给「布局类」声明，绝不给「外观类」声明（`.bib-set-switch-host` 只有 `flex: none` + 定位，这是踩过的坑：同特异性 + 后插入会覆盖宿主，导致 OFF 态开关隐形）。
- 宿主原生组件 API（从 `.../dsh-client-ui-primitives/lib/index.js` 实读）：
  - `DisclosureRow({ icon, title, open, expandable, onToggle, running, expandOnRowClick, previewChevron, keepContentWhenOpen, collapsedContent, children, className, rowClassName, leadingClassName, chevronClassName, titleClassName })`
  - `RiskConfirmation({ open, title, description, acknowledgeLabel, cancelLabel, closeLabel, confirmLabel, acknowledged, disabled, onAcknowledgedChange, onCancel, onConfirm })`（内部是 `Modal` + 勾选确认，未勾选时确认按钮禁用）
  - `Menu` / `MenuItemButton`（复用本插件已有的 `bibSetTimeZonePicker` 用法）

## 4. 验收标准

1. 32 个字段行**全部单行**，行内控件 = 开关 + 一个色块（无 7 色点、无色井、无 hex）。
2. 「原生字段」「插件字段」两组可**独立**折叠展开，互不影响；组头有「已启用 N/M」；默认折叠；搜索输入时自动展开。
3. 「时间与日期」「自定义文字」成独立设置区，对应开关关闭时整区隐藏。
4. 点重置 → 弹出确认（未勾选不能确认）。
5. 点色块 → 弹层：6 预设色 / 自定义 / 恢复默认 / hex，且能真的改色并落盘。
6. `node tests/run-all.mjs` 全绿；真机四视口（1440/1080/900/760）无裁切、无横向溢出、行左沿与宿主原生行一致。

## 5. 补记（2026-09-25 用户看真机后逐条指出）

三处都是「实现没跟上已经拍过的决策」，不是新方向：

1. **三组列表的默认状态：全部收起。**
   本文件决策 2 原本就写的是「默认折叠」，实现时把「插件信息 / 提醒信息」改成了默认展开，理由是「藏在折叠里等于没有入口」。用户看真机后否掉了这个理由：全展开会让设置页一次铺满几十行，反而找不到想看的那一组。改回决策 2 的原意——三组默认收起，想看哪组点哪组；搜索框一有输入仍自动全展开，「找字段」这条路径不受影响。（第三组「提醒信息」是 2026-09-25 从插件组独立出来的，见 `src/constants.js`。）

2. **「组别 = 属于谁」这条规则的真正含义要说清。**
   用户原文：

   > (a) 简洁模式：默认只显示插件信息。
   > (b) 完整模式：展示原生信息和插件信息。
   > 然后通过我们的设置项去开关这个字段。

   即：**组别决定「在简洁模式下能不能出现」，开关只决定「开还是关」，两者互不读写。** 原生组字段只在完整模式出现；插件组字段两种模式都出现；提醒组字段两种模式都出现。这条规则已写进三组的组头说明（`group.native.desc` / `group.plugin.desc` / `group.notice.desc`），设置页不再另设模式开关。

   ⚠️ **本条已被第 6 节取代（2026-09-26）**：「组别」不是显隐栅栏，它只决定字段**住在哪一行**。当年的实现把「组别」读成了「简洁模式下能不能出现」，于是在渲染层散落了 11 处 `if (full)`，才有了第 6 节那次统一。

3. **上下文圆环按「插件信息」对待。**
   它的原型是 DSH 原生 ContextMeter，但已经被本插件接管，并且始终渲染在主行最右端——而主行正是简洁模式保留的那一行。所以它必须归 plugin 组，且渲染门控**只有 `fieldVisible('contextUsage')` 一条，不得再叠加 `full`**。此前写成 `full && fieldVisible(...)`，导致简洁模式下圆环整块消失（用户默认就是简洁模式，所以一眼就看到）。

4. **附带修掉的静默故障：**「版本与更新」区在 `getUpdateState` 读失败时原本直接 `return null` 整块消失。典型触发场景是「包文件已换成新版、DSH 进程仍是启动时载入的旧 host」（桌面端更新插件后没重启），此时旧 host 没有这个 RPC，读必然失败——用户看到的是一张完全没有更新入口的设置页，只能得出「还是得卸载重装」的结论。现在失败时保留板块并说明「重启 DSH 后就会出现」。


## 6. 显示模型定稿：模式只有一个职责（2026-09-26 用户逐项拍板）

### 为什么又要动

用户报：**「已打开自定义文字，简洁模式下看不到，只有完整模式才看得到。」** 这不是又一个 bug，而是第 5 节第 2 条留下的病根 —— 当年把「组别」当成了显隐栅栏，于是渲染层长出 11 处散落的 `if (full)` / `full && fieldVisible(...)`，覆盖了订阅窗口、重置倒计时、本会话花费、余额周期、定价倒计时、预算、免费额度、自定义文字、主时间、世界时间、上下文圆环。同一个字段的显隐同时被三套规则裁决（组别、字段开关、以及一层隐藏的「是不是完整模式」），所以怎么调都还是乱。

用户的判断是：**不能再打补丁，要回到「一套逻辑」重写。**

### 决策记录（用户逐项拍板，原文照录）

> 问：新的显示逻辑，按哪种模型定稿？
- **用户选择：模式只管一行，字段显隐只看开关**
  用户原文：「还是遵循我刚刚说的新逻辑呀，以后只有一套逻辑，就是判断字段属于谁：属于原生信息、提成信息还是插件信息。 1. 简洁模式：只显示插件信息。 2. 完整模式：显示插件信息和原生信息。 3. 提成信息：只是一次性显示，只有在需要的时候，在简洁模式和完整模式下都显示。」
- 用户对设置项列表顺序的回答：**「保持现在的顺序」**（原生信息 → 插件信息 → 提醒信息）
- 用户对「要不要在每条字段后面标注它属于哪种模式」的回答：**「哪条都不标」**

### 定稿的模型

| 层 | 唯一职责 |
| --- | --- |
| 分组（`FIELD_REGISTRY[].group`） | 字段**住在哪一行**：`native`（原生统计行）/ `plugin`（主行）/ `notice`（主行，一次性）。**不是显隐栅栏。** |
| 字段开关 | 字段**显不显示**。唯一裁判。 |
| 模式（`infoDensity`） | **只决定原生统计行那一行参不参与**。与任何字段的显隐无关。 |

推论（全部已由 `tests/test-display-model.cjs` 在渲染层锁死）：
1. 简洁模式与完整模式的**主行字段集合逐字相同**。
2. 原生组字段只出现在原生行；简洁模式收起这一整行，同时收起它的全部字段。
3. 提醒信息与模式无关 —— 当下真有事要提醒就出现，两种模式都显示。
4. 订阅的多个窗口是多个独立开关，两种模式下都由开关裁决，不再有「简洁模式只留最短窗口」这种隐藏规则。

### 配套的工程决定（同批落地）

- **删掉 `FIELD_REGISTRY[].modes`**：它只被测试断言过，产品代码一次都没读 —— 典型的「文档式死字段」，留着只会误导下一个维护者以为模式参与显隐。
- **默认值改为注册表单一生源**：新增 `defaultOff: true`（`customText` / `mainTime` / `worldTime`），`defaultFieldSettings()` 由注册表推导，不再手抄一份字段名单。
- **抽掉三份重复的身份区代码**：余额制、订阅制、云账单制原本各抄一遍「自定义文字 → 服务商锚点 → 时间组」，且各自抄错成 `if (full)`。现在统一走 `pushIdentityGroups()`。
- **`full` 变量只剩一个去处**：`const nativeRowShown = row1Present && full`，只喂给原生行的渲染与 `aria-labelledby`。
- **CI 硬约束**：`tests/test-density-toggle.cjs` 断言源码里不存在 `if (full` 与 `full && fieldVisible`；`tests/test-display-model.cjs` 用真实 `lib/client.js` + React 桩跑三种计费形态与提醒场景，断言两种密度的主行逐字相同。

### 这段历史的价值

三套规则并存时，「修好一个字段」永远只是把混乱挪个位置。判断标准很简单：**同一条规则如果需要靠 grep 找一个分支才能确认，它就不算规则。** 现在模式的含义只有一句话，源码里也只有一处。

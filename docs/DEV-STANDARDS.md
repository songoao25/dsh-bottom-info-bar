# 开发标准（本仓库所有功能开发必须满足）

> 2026-09-25 用户拍板，即刻生效。**动手前先读这一篇，收工前对照自查。**
> 现状与差距见 `docs/CODE-AUDIT.md`（每次审计更新）。

## 一句话版本

| # | 标准 | 一句话判定 |
| --- | --- | --- |
| 1 | **两端适配** | 同一份代码在 DSH 网页端与桌面客户端都能跑；不得只在某一端假设成立 |
| 2 | **简洁优雅** | 同一件事只写一遍；能表格化的不写 if-else 链；能复用的不复制 |
| 3 | **长期可维护** | 换个人接手能读懂；改一处不会漏改另外四处；死代码不留在仓库里 |
| 4 | **体系统一化** | 加功能 = 往既有体系里加一格，**不是**在渲染层再插一段 |

第 4 条是总纲：前三条都是它的推论。判断方法很直白 ——

> **加一个新东西，需要改几个地方？**
> 需要改 1 处（一张表里加一行）→ 合格。需要改 5 处以上 → 这功能还没设计完，先回去设计。

## 1. 两端适配

本插件同时跑在 **DSH 网页端**（浏览器）与 **DSH 桌面客户端**（Electron 渲染进程）。`package.json` 只声明一个 `dsh.client.platform: "web"`，两端复用同一份 bundle，因此**没有第二套代码**，只有两类要求：

**必须做**
- 浏览器 API 一律先探测再使用：`ResizeObserver` / `URL` / `Blob` / `window.confirm` / `AbortSignal.timeout` 都可能缺席，缺了就降级，不能直接抛。
- 路径、环境变量、profile 探测必须走**统一入口**。同一个「用户主目录」在仓库里被推导出不同结果，就会出现「网页端能看到花费、桌面端看不到」这种最难查的 bug。
- 功能不可用时，界面上要说清楚为什么（例：自更新不可用时整块不渲染，而不是摆一个点了没反应的按钮）。

**禁止做**
- 禁止 `process.platform === 'win32' ? ... : ...` 这类**分支式适配**散落在业务逻辑里。要分平台就在统一入口分一次。
- 禁止假设某个目录一定存在（`~/.codex`、`~/.local/share/opencode` 都是可缺席的）。
- 禁止依赖「在网页端能跑」的隐含前提：`window`、`document`、`fetch` 在宿主启动路径上也要有守卫。
- 禁止把「要在终端里执行的命令」当成可用的更新手段下发给桌面端用户。

**现成反例**：`src/host.js` 的 `DATA_DIR` 完全不认 `DSH_HOME`，而 profile 探测认 —— 详见 `docs/CODE-AUDIT.md` P0-3。

## 2. 简洁优雅

**判定方式（按顺序问）**
1. 这段逻辑仓库里**已经有过**吗？→ 复用，不要重写。
2. 这是一组「输入 → 输出」的固定对应吗？→ **做成表**，不要写 if-else 链。
3. 这三处代码长得一样吗？→ 抽一个函数，三处都调用它。

**硬性要求**
- **同一件事只允许一份实现**。semver 比较、原子写文件、读 package.json 版本、HTTP 超时、provider 身份判定 —— 各只准有一份，其余地方 import。
- **常量不写第二遍**。阈值、超时、上限、偏移量集中在 `src/constants.js` 或模块顶部，业务代码里不得出现裸数值（`8 * 3600 * 1000`、`15000`、`60 * 1000` 都属于裸数值）。
- **可表格化的必须表格化**。新增一个服务商如果要改 9 个地方，那这 9 处里至少有 8 处本该是一张表。
- **不写「只有测试在断言」的字段**。注册表里留着代码从不读的字段，等于给下一个维护者下套。

---

## 3. 长期可维护

**硬性要求**
- **函数不超过 200 行**（含）。超了就是「一个函数里塞了一个子系统」，必须按职责拆开；确实无法拆的，必须在 `docs/CODE-AUDIT.md` 的欠账表里登记，且面积只准缩小。
- **不留死代码**：导出但无人调用的 RPC、定义了从不引用的常量、字典里的孤儿 key、有类名没有样式（或反之）—— 发现即删，或明确登记为待删。
- **错误处理形态统一**：同一个模块里不许并存「静默吞掉 / 返回 null / 返回 {error} / 直接 throw」四套策略。选择哪套要有理由，且写下来。
- **注释只描述现在**。注释与代码脱节比没有注释更坏 —— 它会把人带到错误的地方。历史决策写进 `docs/DECISIONS-*.md`，不要留在业务代码里冒充现状。
- **样式值只能来自令牌**。同一张样式表里既定义 `--bib-x: 16px` 又写 `padding: 16px`，规则就死了。

## 4. 体系统一化

这一条针对「随便乱插代码」。本仓库已经吃过两次同型事故，都是同一个成因：

> **渲染层自己长出了一套规则，而它不在任何注册表里。**

- 显示模型（2026-09-25）：渲染层散落 11 处 `if (full)`，让「简洁模式」偷偷多了一套字段显隐规则 → 用户报「自定义文字在简洁模式看不到」。整改后：字段显隐只由字段开关决定，模式只剩一处用处。详见 `docs/DECISIONS-SETTINGS-REDESIGN.md` 第 6 节。
- 字段着色：颜色规则必须由 `FIELD_REGISTRY` 生成（`buildFieldColorCss`），不得在渲染处手写色值。

**硬性要求**
- **加字段 = 往 `src/constants.js` 的 `FIELD_REGISTRY` 加一行**。设置页与信息栏都必须能从注册表推导出来；如果发现某一侧还得手写，那是那一侧的结构问题，先修结构再加字段。
- **一个概念只允许一张表**。窗口 key → 字段 id / 标签 / 优先级，只能有一张 `WINDOW_META`，不许复制成四张。
- **服务商只允许一处定义**。`PROVIDERS` 是唯一来源，身份、订阅源、账单源、显示名、币种全部从它派生，不许再加 if-else 链。
- **样式表只允许一份源**。信息栏与设置页共用同一套度量令牌，不得各建一套前缀后再互相串台。
- **禁止「按需新增分支」式打补丁**。当修一个字段需要再加一个 `if`，说明规则本身错了 —— 回到「谁决定它显示」这个层面重新设计，不要在渲染处再插一段。

## 开工 / 收工清单

**动手前**
1. 读 `AGENTS.md`（发布与守卫）→ 读本篇（标准）→ 读 `docs/CODE-AUDIT.md`（欠账）。
2. 判断这次改动属于「往体系里加一格」还是「要新开一套体系」。后者必须先出设计、先拍板（重大决策走弹窗）。
3. 估算要改几处。超过 5 处 → 停下来重新设计。

**收工前**
1. `node scripts/build.mjs && node tests/run-all.mjs` 全绿。
2. 自查四条：两端都想到没有？同一件事有没有第二份实现？有没有留下死代码？是加了体系还是插了分支？
3. 更新文档：行为变了写 `docs/`，决策变了写 `docs/DECISIONS-*`，欠账变了更新 `docs/CODE-AUDIT.md`。

## 例外与欠账

历史代码不可能一天改完。**允许存在欠账，但不允许欠账变多。**
所有已知欠账在 `docs/CODE-AUDIT.md` 里逐条登记（位置 + 现状 + 目标）。规则：

- 新增代码不得引入新的欠账。
- 触碰某个模块时，顺手把它名下的欠账消掉（童子军原则）。
- 每次发布复盘时核对一次：欠账清单是变短还是变长了。
